# Order notifications and digital files

Apply the order-management migration before `20261022010000_notifications_digital.sql`. New tables use RLS with no browser policies and explicit `jelly_backend` grants/policies when that role exists. Enable each store through `StoreOrderManagementSettings.enabled` before its notifications are queued. Enabling a store does not send historical emails.

Mount the factories in `commerce/notification-routes.ts` under `/api/stores/:storeId/order-notifications`, `/api/stores/:storeId/orders`, `/api/stores/:storeId/digital-products`, and `/api/public/stores/:storeId/digital`, respectively. The worker calls `notificationService.runWorker()` every minute. It claims one job at a time with row locks and five-minute leases, verifies the lease just before sending, and stops claiming after three minutes. It never holds database transactions while contacting SMTP. A successful provider response means **accepted**, not delivered.

Production requires an SMTP transport with a verified domain, credentials and a platform sender; store branding only changes presentation and reply-to. Capture transport is intended for development. Stable Message-ID values help provider investigation but are not an SMTP idempotency guarantee. Lost DATA replies and expired worker leases become `UNCERTAIN`; investigate provider logs before explicitly resending. Definite failures retry exponentially up to eight attempts. Order timelines and notification-list APIs expose failures.

Inject a persistent secret of at least 32 characters for digital tokens. Keep this secret stable across instances and restarts. Configure `publicBaseUrl` as the frontend origin and `apiBaseUrl` as the backend origin (including any Firebase function prefix). Tokens are derived per entitlement using HMAC; only SHA-256 hashes are persisted. Tokens never appear in merchant list responses.

Use `supabasePrivateDigitalStorage(client, bucket)` with backend credentials and a **private** bucket. The adapter refuses public buckets. Local filesystem storage is for development and must be outside any public/static directory. Uploaded files are capped at 50 MB and served as attachment bytes through backend authorization, never through a public/signed media URL. Every request rechecks verified payment, store boundary, token, revocation, expiry and remaining count. The final check and increment run under a row lock, preventing concurrent requests from exceeding a limit. A download attempt means authorization to send bytes, not a guarantee that the client received every byte.

Payment success grants entitlements from the purchased `OrderItem.fulfillmentType` snapshot and active product assets. A digital-only order becomes fulfilled when every item has access; mixed orders retain physical fulfilment separately. Existing entitlements retain their file even when the product asset is archived. Cancellation and full refunds revoke access. Successful `REFUND_PROCESSED` events with explicit `variantIds` revoke matching digital items. Monetary partial refunds do not imply which item was refunded. `digitalService.revokeItems(storeId, orderId, variantIds)` is also available to verified financial callers.

Product delivery settings appear on the existing edit-product page. Create a product, choose Digital download, then upload its private file. Uploading a file does not publish or modify catalog media. Enforce active-file availability before accepting checkout for a digital product.
